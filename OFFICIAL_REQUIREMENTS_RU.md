# Официальные требования и ограничения решения

Статус: обязательный рабочий контракт команды. Перед новым экспериментом,
изменением inference или подготовкой submission необходимо сверяться с этим
файлом. Если старые документы репозитория ему противоречат, приоритет имеют
официальные материалы организаторов и этот конспект.

Проверено по:

- `../Вопросы и ответы Бизнес 7. Фалькон Тех.xlsx`, лист
  `Объединённые вопросы участников`, прежде всего строки 4, 6–13, 15–20,
  24, 28–45 и 51–53;
- `../evaluate.py`;
- `../example_submission.zip`;
- README выданного датасета.

## 1. Главный инвариант: потоковая независимость query

Для ранжирования одного query разрешено использовать только:

1. текущее изображение query;
2. всю статическую `test_gallery`;
3. данные и модели, полученные на train и разрешённых внешних источниках;
4. состояние, заранее построенное исключительно по статической gallery.

Запрещено:

- использовать изображения, embeddings, ранги, предсказания или статистику
  других `test_query`;
- считать query-query similarity;
- кластеризовать `test_query`;
- объединять несколько query в семью/треклет;
- делать глобальное назначение gallery сразу всем query;
- использовать результаты обработки предыдущих query для последующих;
- подбирать параметры по скрытым ответам или сообщениям от организаторов;
- использовать `vehicle_id` закрытого теста в любой форме.

Формат запуска пакетный, но это не разрешает трансдуктивную обработку всего
батча. Потоковую независимость организаторы проверяют по исходному коду.

Разрешено:

- TTA одного текущего изображения;
- первичный поиск текущего query по gallery;
- k-reciprocal или другой reranking внутри top-K текущего query;
- pairwise/local-feature verifier для пар «текущий query — gallery candidate»;
- предварительное индексирование, DBA, кластеризация и прототипы, построенные
  только по статической gallery;
- перенос доказательств между элементами заранее построенной gallery-группы.

### Осторожно с термином query expansion

В Q&A организаторы отдельно написали «Query expansion — запрещён», связывая
его с использованием других query. Чтобы не спорить о терминологии, в финальном
решении нельзя включать операцию, названную или реализованную как query
expansion. Безопасная замена — явно документированный per-query top-K reranker,
который не меняет query по информации других запросов.

## 2. Ordered-block результат 0.95912 сдавать нельзя

Удалённый эксперимент с ordered blocks предполагал, что соседние строки query и
gallery образуют непрерывные блоки одного `vehicle_id`, сегментировал весь набор
query и монотонно сопоставляет query-блоки gallery-блокам. Это одновременно:

- использует порядок строк конкретного тестового файла как скрытую identity-
  разметку;
- обрабатывает другие test-query для ответа на текущий query;
- нарушает потоковую независимость;
- не переносится при перемешивании строк или другой нарезке скрытого теста.

Результат `0.95912` — диагностический exploit/oracle, а не допустимое качество
модели. Его нельзя включать в финальный inference, submission или заявлять как
ожидаемый closed-test score.

Фраза организаторов «закрытый тест имеет ту же структуру» означает одинаковые
CSV-колонки, формат изображений, протокол query/gallery и примерно 20% open-set.
Она не гарантирует сохранение порядка строк, непрерывных identity-блоков,
числа кадров одной машины или взаимного расположения query и gallery.

## 3. Основная ranking-метрика

- Основная метрика: `mAP@10` из `submission.csv`.
- Вес в итоговой оценке: 45%.
- Для каждого query junk удаляется до усечения до top-10.
- Junk: gallery-изображение, у которого одновременно совпадают `vehicle_id`
  и `camera_id` с query.
- Другая машина с той же камеры остаётся валидным негативом.
- AP делится на `min(n_valid_positives, 10)`.
- Усреднение AP — macro по query с хотя бы одним валидным позитивом.
- Query без валидного cross-camera positive исключается из mAP и Rank, а не
  получает AP=0.
- Полный mAP и mINP из `embeddings.npy` справочные и баллов не добавляют.
- При равных score для embeddings используется стабильный порядок строк
  `test_gallery.csv`.

Практическое следствие: оптимизировать нужно официальный `mAP@10`, но
валидация обязана сохранять потоковую независимость.

## 4. Open-set и режим отказа

- В закрытом тесте около 20% query не имеют своей машины в gallery.
- Они не помечены во входных файлах.
- Для остальных 80% гарантирован минимум один cross-camera positive.
- В открытом test у каждого query есть пара, поэтому по нему нельзя калибровать
  отказ.
- Локальная open-set validation должна искусственно оставлять примерно 20%
  identity только в query и полностью удалять их из gallery.

Официальная логика `candidates.csv`:

- решение принимается на уровне query, не отдельной пары;
- учитывается только строка с максимальным `confidence` для query;
- несколько дополнительных кандидатов не влияют ни положительно, ни
  отрицательно;
- отказ кодируется полным отсутствием строк для `query_id`;
- организаторы не применяют свой порог: наличие строки уже означает принятое
  командой решение;
- `confidence` может иметь любую числовую шкалу, больше = увереннее;
- F1 и TNR считаются micro по всей выборке;
- `candidate_score = 0.7 * F1 + 0.3 * TNR`;
- блок режима отказа весит 10% итоговой оценки.

`submission.csv` и `candidates.csv` — независимые выходы. Даже при отказе в
`candidates.csv` в `submission.csv` всё равно обязательно записываются десять
кандидатов.

## 5. Форматы файлов сдачи

### submission.csv

- без заголовка;
- одна строка на каждый query;
- формат: `query_id,gallery_id_1,...,gallery_id_10`;
- ровно десять уникальных валидных gallery ID;
- порядок — финальный порядок после разрешённого reranking.

### candidates.csv

- заголовок обязателен;
- фиксированные столбцы: `query_id,gallery_id,confidence`;
- отказ — отсутствие строк данного query;
- пустой `gallery_id` и специальные значения использовать нельзя.

### embeddings.npy

- двумерный массив `float32`;
- строки: сначала все query в исходном порядке `test_query.csv`, затем все
  gallery в исходном порядке `test_gallery.csv`;
- для открытого теста ожидаемая форма `(1110 + 750, D) = (1860, D)`;
- `D` выбирает команда;
- L2-нормализация при сохранении не обязательна: `evaluate.py` нормализует
  самостоятельно;
- строка обязательна для каждого `image_id`.

## 6. Структура данных

- Один `image_id` = один файл = один размеченный автомобиль.
- Формулировка PDF о нескольких ТС в одном кадре признана ошибкой.
- Query и gallery находятся в отдельных CSV.
- BBox автомобиля предоставляется; собственная детекция не требуется.
- Минимального допустимого размера BBox нет.
- Закрытый тест собран тем же пайплайном и имеет те же CSV-колонки и формат
  файлов, но содержит другие скрытые изображения и разметку.
- Утверждение о пересечении строк train и test организаторы не подтвердили;
  предполагаемого пересечения эксплуатировать нельзя.

## 7. Camera ID

`camera_id` из train разрешено использовать для:

- PK-sampling;
- cross-camera validation;
- корректного junk-протокола локальной оценки.

Нельзя передавать `camera_id` или производный от него признак модели как
inference-вход. В test этого поля нет. Любая камера-зависимая эвристика должна
считаться недоступной, если она требует истинного test camera ID.

## 8. Номерные знаки

- Выданные изображения уже содержат blur номеров и лиц.
- Дополнительные маски организаторы не предоставляют.
- Внешние публичные Vehicle ReID данные могут содержать читаемые номера;
  предварительно маскировать их организаторы не требуют.
- Финалистов проверят на контрольной версии, где номерная область залита
  сплошным цветом.
- Существенное падение качества укажет на использование остаточных артефактов
  номера и будет разбираться на защите.

Следствие: обучение должно быть устойчиво к закрытию номерной зоны. Допустимы
Random Erasing, Cutout и consistency между обычным и замаскированным видом, но
нельзя строить специальный распознаватель остаточной текстуры номера.

## 9. Внешние данные и веса

Разрешены публичные веса и датасеты, если можно указать:

- URL;
- автора/организацию;
- точную версию, commit или tag;
- при возможности checksum.

Допустимы DINOv2/DINOv3, gated-access источники, CC BY-NC и публичные Vehicle
ReID датасеты. Запрещены приватные репозитории, внутренние датасеты и веса без
проверяемой публичной ссылки. Требование относится ко всем вспомогательным
моделям, а не только к основному backbone.

## 10. Производительность и упаковка

Финальный стенд:

- NVIDIA RTX A5000, 24 ГБ VRAM;
- CUDA driver 12.2;
- 2 × Intel Xeon Gold 6338;
- GPU доступна в Docker через `--gpus all`.

В latency `extract()` входят чтение, декодирование, crop, preprocessing,
forward, postprocessing и L2-нормализация. Поиск по gallery и reranking в
официальный performance score не входят.

- latency batch=1 ≤ 40 мс: полный балл;
- 40–80 мс: линейное снижение;
- > 80 мс: 0 за latency;
- лучший throughput ≥ 100 FPS: полный балл;
- 50–100 FPS: линейное снижение;
- < 50 FPS: 0 за throughput;
- performance: 10% latency + 10% throughput.

Суммарный размер всех файлов весов inference должен быть ≤2 ГБ. Считаются
основная и вспомогательные модели, ensemble, reranker и файлы `.pt`, `.pth`,
`.bin`, `.onnx`, `.engine`, `.plan`, `.safetensors`, `.ckpt`, `.trt`, `.pb`,
`.tflite`, `.npz`. Превышение лимита не штрафуется плавно: решение не допускают
к performance-оценке.

`docker build` может использовать интернет. Финальный запуск и inference
полностью офлайн. Версии зависимостей фиксируются точно; скачиваемые веса
фиксируются URL/версией и checksum. Обязательный inference запускается одной
командой. Веб-интерфейс и внешняя БД для основной оценки не требуются.

## 11. Разрешённая целевая архитектура

Рекомендуемый поток:

1. быстрый global/part extractor;
2. заранее построенные embeddings, локальные признаки и группы static gallery;
3. поиск top-25/top-50 для одного текущего query;
4. vehicle-specific pairwise/local verifier кандидатов;
5. group-aware score propagation только внутри static gallery;
6. финальный top-10 для `submission.csv`;
7. отдельный accept/reject head для `candidates.csv`.

Reject head следует обучать на независимых 20%-open-set эпизодах. Полезные
признаки: абсолютный top-1 score, margin top-1/top-2, отрыв от top-5, согласие
нескольких визуально разных моделей, pairwise score, поддержка gallery-группы и
оценка качества query.

Текущий подтверждённый профиль сдачи `speed`:

- `mAP@10 = 0.836126`;
- `Rank-1 = 0.804762`;
- `Rank-5 = 0.926279`;
- использует только текущее query и заранее построенные признаки static gallery;
- verifier получает только текущее query и один gallery candidate;
- не использует другие query, test camera ID или порядок CSV;
- validation воспроизводится в
  `outputs/score_optimized_speed/validation.json` на пяти locked seed.

Refusal-калибратор привязан к фактическому финальному top-1. Протокол содержит
один query на identity, 20.13% unknown query и gallery из 750 изображений.
Порог выбирается на tune OOF при ограничении `TNR >= 0.94`. На отдельных
confirmation seed: F1 `0.836127`, TNR `0.951613`, официальный компонент
`0.870773`. Полный отчёт находится в
`outputs/score_optimized_speed/refusal_calibration.json`.

Это локальная validation-оценка, не leaderboard score.

## 12. Checklist перед каждым экспериментом

Эксперимент допускается к сравнению только если на все вопросы ниже ответ
«да»:

- [ ] Для ответа текущему query не читаются embeddings/ранги других query.
- [ ] Перемешивание строк query не меняет ответ для каждого изображения.
- [ ] Удаление всех остальных query не меняет ответ текущего query.
- [ ] Любая общая структура построена только по static gallery.
- [ ] Истинный или предсказанный из метаданных test camera ID не используется.
- [ ] Validation разделена по identity и имитирует cross-camera junk-фильтр.
- [ ] Tune и confirmation используют разные identity-disjoint эпизоды/seeds.
- [ ] Ranking считается официальным mAP@10, а не только полным mAP.
- [ ] Отдельно проверяется 20%-open-set F1/TNR.
- [ ] Нет зависимости от порядка строк, имён файлов или размера конкретного test.
- [ ] Нет зависимости от остаточных артефактов номерной зоны.
- [ ] Все внешние источники документированы URL и версией.
- [ ] Сумма inference-весов не превышает 2 ГБ.
- [ ] `submission.csv` содержит ровно 10 кандидатов для каждого query.
- [ ] Отказ выражается только отсутствием query в `candidates.csv`.
- [ ] Решение воспроизводимо офлайн после сборки контейнера.

## 13. Запрещённые результаты нельзя смешивать с честной таблицей

В отчётах всегда разносить отдельно:

- `official-streaming`: разрешённая оценка, кандидат на финальную сдачу;
- `research-transductive`: использует другие query, только диагностика;
- `ordered-block exploit`: использует порядок строк, только демонстрация утечки;
- `oracle`: использует ground truth, только верхняя граница.

Нельзя называть transductive, ordered-block или oracle score «текущим качеством
модели» без явной маркировки.

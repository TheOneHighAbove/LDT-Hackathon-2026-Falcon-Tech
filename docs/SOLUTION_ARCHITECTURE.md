# Архитектура, история выбора и направления развития

## 1. Краткое резюме

Финальное решение — offline Vehicle ReID pipeline: по одному изображению и BBox
автомобиля оно формирует дескриптор, ищет похожие изображения в статической
gallery, переупорядочивает короткий список локальными и групповыми моделями и
отдельно решает, достаточно ли надёжен итоговый top-1.

Для сдачи выбран профиль `speed`:

| Метрика | Значение на locked validation |
|---|---:|
| mAP@10 | **0.836126** |
| Rank-1 | 0.804762 |
| Rank-5 | 0.926279 |
| Rank-10 | 0.957319 |
| Размер весов | 244 640 363 байта |

Это результаты identity-disjoint локальной validation, а не скрытого теста.
Профиль `quality` достигает mAP@10 `0.841086`, Rank-1 `0.812875` и Rank-5
`0.936684`, но тяжелее (`422.9 MB`) и медленнее.

## 2. Поток обработки

```text
JPEG + BBox
   │
   ├─ shared Pillow crop/resize ── OSNet ───────── identity/metric/parts
   ├─ shared Pillow crop/resize ── DINOv2 B/14 ─── CLS/regions/patch tokens
   ├─ shared Pillow crop/resize ── ConvNeXt-Tiny ─ global/local descriptor
   └─ пятизонный HSV descriptor
                         │
                         ▼
              объединённый L2-дескриптор
                         │
                         ▼
            cosine retrieval по static gallery
                         │ top-50/top-25
                         ▼
 DINO token/patch matching + pair verifier + LambdaRank + family GNN
                         │
                         ▼
                    финальный top-10
                         │
                         └─ logistic open-set policy → принять top-1 / отказать
```

### Извлечение признаков

Три backbone выбраны не ради количества моделей, а как разные типы сигнала:

- **OSNet** специализируется на identity-признаках и частях автомобиля;
- **DINOv2 ViT-B/14** даёт сильное обобщение, региональные признаки и patch
  tokens для локального сопоставления разных ракурсов;
- **ConvNeXt-Tiny** добавляет независимый глобальный и локальный CNN-сигнал;
- **HSV по пяти зонам** дешёво сохраняет информацию о распределении цвета.

Backbone экспортированы в self-contained TorchScript. Изображение декодируется
один раз, crop переиспользуется, а независимые GPU-ветки могут выполняться в
CUDA streams. Patch tokens берутся из того же forward, отдельного второго
прохода по DINO нет.

### Retrieval и reranking

Первичный cosine retrieval отвечает за recall короткого списка. Далее работают
компактные модели только по top-25/top-50:

- DINO patch/token cross-matching сравнивает локальные элементы кузова;
- pair verifier проверяет совместимость конкретной пары query–gallery;
- LambdaRank учит порядок кандидатов непосредственно внутри query-группы;
- family GNN и gallery linker используют связи только внутри заранее известной
  статической gallery.

Другие test query, test camera ID и порядок строк CSV не используются. Это
важно и для правил, и для production-сценария потоковых запросов.

### Open-set отказ

Отказ не меняет `submission.csv` и mAP. Логистическая модель оценивает
корректность уже выбранного top-1 по восьми сигналам: итоговым score и его
разрывам, cosine и его разрывам, плотности и изолированности кандидата в
gallery. Порог `0.6307946113` выбран на group-OOF при ограничении `TNR >= 0.94`.

Locked confirmation:

| Метрика отказа | Значение |
|---|---:|
| F1 | 0.836127 |
| TNR | 0.951613 |
| Precision | 0.978214 |
| Recall | 0.730081 |
| `0.7 × F1 + 0.3 × TNR` | **0.870773** |

Предыдущая policy давала `0.862576`; перекалибровка добавила `+0.008196` к
компоненту отказа. На публичном test принято 975 из 1110 запросов и отклонено
135; без test labels это не является оценкой точности.

## 3. Почему выбрана именно эта архитектура

1. **Сначала максимизировался recall.** Разные backbone полезнее ещё одного
   почти идентичного embedding: CNN, специализированный ReID и transformer
   ошибаются не полностью одинаково.
2. **Затем оптимизировался короткий список.** Среди 1107 Rank-1 ошибок на пяти
   locked эпизодах в 689 случаях (`62.2%`) правильный ответ уже находился на
   местах 2–5, ещё в 176 (`15.9%`) — на местах 6–10. Поэтому локальный reranker
   имеет более ясную цель, чем бесконечное расширение глобального ансамбля.
3. **Gallery-граф используется только там, где это легально.** Повторные фото
   внутри статической gallery дают полезное семейство, но query-query связи не
   строятся.
4. **Качество отделено от итогового score.** CLIP повышает mAP примерно на
   `0.0053`, но ухудшает latency, throughput, VRAM и размер. Поэтому он оставлен
   в `quality`, а сдаваемый контейнер использует `speed`.
5. **Отказ калибруется после reranking.** Уверенность первичного cosine не
   соответствует вероятности правильности финального top-1.

## 4. Проверенные, но не вошедшие идеи

| Идея | Решение и причина |
|---|---|
| CLIP ViT-B/16 и CLIP top-25 | Оставлены только в `quality`: выигрыш около `+0.0053 mAP` недостаточен относительно стоимости по скорости и памяти. |
| DINOv3 и более крупный ViT-L | Не вошли в `speed`: существенно тяжелее, а устойчивого выигрыша, оправдывающего latency и сложность финального Docker, не зафиксировано. |
| Flip-TTA | Удалён из release-пути: почти удваивает дорогую часть forward; подтверждённого выигрыша итогового score на locked протоколе нет. |
| Дополнительные embedding-ансамбли | Не включены, когда давали сильно коррелированный порядок и не показывали стабильного выигрыша на нескольких locked seeds. |
| Наивное продвижение «часто встречающегося семейства» | Глобальный boost слишком легко поднимает семейство похожой чужой машины. Сохранён только ограниченный tune-locked gallery consensus внутри короткого списка. |
| Query-query clustering | Запрещён постановкой для потокового режима и создаёт зависимость ответа от соседних test query. |
| Истинный/predicted test camera prior | Не используется: camera ID нужен только для training/validation junk mask и анализа. |
| Признаки порядка CSV | Отклонены как утечка, не имеющая бизнес-смысла. |
| Распознавание номера | Намеренно не используется: решение должно опираться на внешний вид автомобиля, а не остаточную текстуру номера. |
| RootSIFT, SigLIP и CLIP-ReID exploratory branches | Не перенесены в release: не было воспроизводимого locked-выигрыша поверх текущих высоко коррелированных визуальных сигналов. |

Для идей без сохранённого locked-отчёта намеренно не приводится искусственная
цифра прироста.

## 5. Текущие проблемы

### Ошибки качества

- `21.9%` Rank-1 ошибок не имеют правильного ответа даже в top-10: здесь одного
  reranking недостаточно, нужен лучший initial retrieval.
- Сильная смена ракурса остаётся главным классом ошибок: зад одного автомобиля
  может быть менее похож на его перед, чем на зад другой машины той же модели.
- Самый маленький квартиль BBox имеет Rank-1 `0.760395`, самый крупный —
  `0.833568`: разрыв составляет 7.3 процентного пункта.
- Дополнительные причины: перекрытия, ночной свет, блики, crop, одинаковые
  комплектации и изменение рекламы/ливреи между камерами.
- Возможен domain shift open-set: доля и тип неизвестных автомобилей на
  закрытом тесте могут отличаться от validation.

### Производительность: что именно известно

Официальная граница `extract()` включает JPEG I/O, decode, BBox crop,
preprocessing, forward, postprocessing и L2 normalization. Поиск и reranking в
performance timing не входят. Максимум требует одновременно batch-1 `<=40 ms`
и throughput `>=100 FPS`.

Сопоставимые строгие измерения на RTX 4060:

| Runtime | Batch-1 median | Лучший throughput |
|---|---:|---:|
| PyTorch 2.5.1/CUDA 12.1, финальный Docker | 50.98 ms | 101.04 FPS |
| PyTorch 2.11/CUDA 12.8, эксперимент | 41.83 ms | 124.05 FPS |

Около `9 ms` и `23 FPS` объясняются runtime. Старые `36.99 ms / 119.47 FPS`
не сопоставимы: использовались 10, а не 50 warmup, другой способ усреднения и
не учитывался пятизонный HSV. Замена `np.histogram` на эквивалентный
`np.bincount` экономит локально около `0.6 ms` без изменения признака.

Контрольный запуск заново собранного Docker обработал 1860 изображений за
`23.992 s` (`77.53 image/s`) и выполнил весь ranking за `12.769 s`. Это проверка
полного dataset-run, а не официальный синтетический throughput benchmark, и
эти числа нельзя смешивать с таблицей выше. Verifier завершился со
`status: ok`.

RTX A5000 организаторов имеет примерно в `1.85×` большую пиковую FP32
производительность, чем RTX 4060, однако около половины локального batch-1
занимает CPU preprocessing. Поэтому 40 ms на A5000 реалистичны, но 20/20 можно
подтвердить только фактическим замером на стенде. Один Docker не пытается
автоматически переключать две версии PyTorch: два окружения увеличили бы образ
и риск сборки; результат нового runtime сохранён как эксперимент.

Незначительные изменения float-результатов между CUDA-запусками возможны.
Последний повторный запуск сохранил тот же top-1 для `99.55%` query; корректность
каждого bundle проверяется его собственными SHA-256 и fail-closed verifier, а не
обещанием побайтового совпадения между разными GPU/runtime.

## 6. Приоритеты дальнейшего развития

1. **Сначала замерить неизменённый контейнер на A5000.** Не менять модель до
   получения официального разложения CPU/GPU latency.
2. **Отдельная ветвь для маленьких BBox.** High-resolution teacher или
   distillation только для сложных малых объектов с контролем latency.
3. **View-aware local matching.** Обучать перед↔зад и бок↔перед соответствия на
   train-камерах, не передавая camera ID в inference.
4. **Hard-case reranker.** Сосредоточить обучение на 689 случаях, где верный
   ответ уже находится на позициях 2–5, используя identity-disjoint OOF.
5. **Улучшить первый этап для оставшихся 21.9% ошибок.** Нужен новый
   действительно независимый сигнал, а не ещё один высоко коррелированный
   backbone.
6. **Проверить быстрый runtime.** Только после подтверждения точного драйвера
   стенда протестировать отдельный build PyTorch 2.11/CUDA 12.8; не помещать две
   версии PyTorch в один release.
7. **Перекалибровать отказ на production base rate.** Мониторить F1/TNR,
   reliability и drift, не подбирать порог по числу отказов на test.
8. **Масштабирование gallery.** Для сотен тысяч/миллиона объектов перейти на
   FAISS IVF/PQ, хранить полные patch tokens только для top-K и контролировать
   recall@K, p50/p95/p99 и дрейф камер.
